# IndicRAG v2.6 Plan + Optimization Recommendations

Derived from a full-codebase review (query/serving path, storage/ingestion path, agent layer,
git history) read through the *Designing Data-Intensive Applications* lens. Companion to
`docs/ARCHITECTURE_REVIEW_v2.4.md` — items are cross-referenced to its IDs where they exist.

## Ground truth (what the code does today)

- **Serving**: single uvicorn worker (`start_server.py:154`), whole pipeline off-loop via
  `run_in_threadpool`. Faithfulness NLI runs synchronously on every `/query`/`/chat` answer
  (`rag.py:1027,1131,1283`). Cross-encoder rerank costs ~11 s per 15 candidates on CPU
  (`rerank.py:19`). Failover chain worst case ~180 s, deliberately unbounded by the reflexion
  budget (`config.py:395-402`).
- **Caching**: three TTL-LRU caches (`cache.py`) + query-embedding LRU with in-flight coalescing
  (`embeddings.py:134-179`) + opt-in Gemini prompt caching (`gemini_cache.py`, off by default).
  `_post_ingest_refresh` clears retrieval + tool caches but **not** `llm_cache`
  (`cache_refresh.py:37-40`).
- **Indexes**: BM25 inverted index with tombstone deletes; `df` is recomputed per query term by
  scanning posting lists against tombstones (`bm25_search.py:146`); compaction only via full
  rebuild. ChromaDB HNSW (cosine, ef=100/M=16); `chroma_db/` currently holds ~25 orphaned UUID
  segment directories from reset/recreate cycles that Chroma never garbage-collects.
- **System of record**: `ingest_log` in SQLite (WAL, one connection + one global `_db_lock`,
  commit-per-call — `persistence.py:17,113`). `reindex.py` replays it. Deletes cascade
  Chroma → BM25 → log, each step best-effort (`vector_store.py:497-527`).
- **Already shipped in v2.5** (do not re-do): derived-view indexing + replay, circuit breaker +
  sparse-only degraded mode, leased/reaped jobs, CAS watch claims, index provenance stamps,
  per-stage Prometheus metrics, integration seam suite, `_post_ingest_refresh` (cache_refresh.py),
  `_flatten_contents` for OpenRouter content serialization (openrouter.py:19-36), double-checked
  locking on `_init_backends` (llm_client.py:56-61).

## Part 1 — Optimization recommendations

### A. Tail latency (DDIA ch1: engineer p99, not averages)

| # | Change | Where | Why |
|---|--------|-------|-----|
| A1 | Move faithfulness NLI off the critical path — run post-response, or gate behind a request flag. **`/query` and `/chat` only** (`rag.py:1027,1131`): the agent site (`rag.py:1283`) feeds `AGENT_FAITHFULNESS_ACCEPT` in the reflexion gate (`agent/nodes/reflexion_evaluator.py:186`) and must stay inline | `rag.py:1027,1131` | Removes the largest variable tail component (seconds per answer) whose value is informational on the non-agent paths |
| A2 | Two-stage reranking: cheap first pass (smaller CE or reuse dense scores) → bge-reranker-v2-m3 only on top ~8 | `rag.py:451-456`, `rerank.py` | ~11 s floor per cold query is the single biggest CPU cost; also consider skipping rerank on retrieval-cache hits |
| A3 | Dedicated `anyio.CapacityLimiter` for `/query*`,`/chat*`,`/agent*`; shed with 429 + Retry-After | route handlers | Heavy traffic today starves the shared pool, queuing `/health` and job polls behind 90 s RAG work (= review item B4 admission control) |
| A4 | Deadline-aware failover: thread remaining budget through `generate_with_failover`, skip attempts that cannot finish | `llm_client.py:111-125` | The code itself names this fix (`config.py:400-402`); also propagate cancellation so abandoned requests stop burning quota (= C7) |
| A5 | SSE backpressure: `put_nowait` with drop-oldest-chunk semantics for non-terminal events; cap concurrent stream-producer threads | `sse_utils.py:41` | A slow client blocks the producer thread for 30 s per chunk, pinning a Gemini connection for minutes |

### B. Storage-engine hygiene (DDIA ch3: compaction is not optional)

| # | Change | Where | Why |
|---|--------|-------|-----|
| B1 | Maintain live per-term `df` counters on add/tombstone; auto-compaction (off-thread full rebuild) when deleted/live > 20% | `bm25_search.py:81-161` | Tombstoned postings are rescanned per query term today — classic un-compacted LSM read amplification |
| B2 | Segment-GC maintenance command: diff UUID segment dirs against `collections` metadata, remove unreferenced | new util | ~25 orphaned HNSW segment trees on disk now; Chroma resets never reclaim them |
| B3 | Batch transactions for bulk log writes (reindex replay: 1 tx per N papers); separate read connections to actually use WAL | `persistence.py` | Single connection + global lock + commit-per-call forfeits every WAL benefit; fsync per mutation |
| B4 | Convert embeddings per 256-batch slice instead of `tolist()` on the whole matrix | `vector_store.py:302` | Pure memory-spike win on bulk ingest |

### C. Consistency & staleness (DDIA ch5/7: read-your-own-writes, end-to-end audit)

| # | Change | Where | Why |
|---|--------|-------|-----|
| C1 | Add `llm_cache.invalidate()` to `_post_ingest_refresh` | `cache_refresh.py:37-40` | Deleted-paper answers are servable for up to 10 min today — sharpest invalidation gap in the system |
| C2 | Rewrite `check_db.py` into a real reconciler: per-paper `count(chroma)` vs `len(log.ids)` vs BM25 id membership; wire into `/quality` | `check_db.py` (dead duplicate-check today — Chroma ids are primary keys) | Automates the exact divergence classes that caused the v2.5 rollback bugs; DDIA ch12: verify derived views against the log end-to-end |
| C3 | Make delete-cascade failures loud + surfaced (degraded-quality signal), not warn-and-continue | `vector_store.py:510-526` | Silent ghost citations / replay resurrection on best-effort step failure |
| C4 | Allow scoped/tag-filtered queries to hit the retrieval cache (key already hashes the filter) | `rag.py:324` | Every paper-scoped repeat query pays the full pipeline for no reason |
| C5 | Make `purge --db` coherent: also clear `ingest_log` + BM25 gz cache | `purge.py:131-145` | Today a purge leaves a phantom corpus the log claims is replayable |

### D. Ingest throughput & derived views (DDIA ch10/11: batch, then materialize)

| # | Change | Where | Why |
|---|--------|-------|-----|
| D1 | Parallelize arXiv enrichment (2–3 workers) + persistent title→metadata cache table | `metadata_enrich.py:23` | Serial 1 s/paper delay adds N seconds to every bulk run |
| D2 | SQL mirror `(paper_id, title, year, chunk_count)` maintained at `_record_ingest` | `persistence.py`, callers of `find_similar_paper` / `get_paper_chunk_counts` | Kills two O(corpus)-in-Python scans; dedup checks and `/stats` become index lookups |

### Quick-win set (ship as v2.5.x patches)

C1, C4, B4, D2, ColBERT startup warm-up when `USE_COLBERT_RERANK=true`, WAL checkpoint on shutdown,
atomic tmp+rename for the BM25 cache save, stale-docstring fixes (`deps.py:4-5`).

### Cross-cutting debt sprint (parallel track)

- Tests for `execute_python`'s AST validator (`agent/tool_executor.py:211-289` — most security-sensitive
  code in the repo, zero tests), `query_planner` decomposition, `tool_selector` routing +
  `_ensure_corpus_coverage`, load/admission behaviour.
- Verify still-open `bug_report.md` findings against current code before re-filing:
  BUG-01/02, 08, 09/10, 13, 14, 15/16. (BUG-03 and BUG-05 are already fixed in v2.5.)
- Doc sync: `repo.md` still describes v2.4; `session_context.md` is historical. Update or archive.

### Deliberately NOT recommended (yet)

- **Qdrant/pgvector migration or HNSW retuning** — provenance stamps make any future migration a
  replay, but current corpus scale doesn't justify it; revisit around ~1M chunks. Note: M is
  immutable after collection creation (`vector_store.py:151-153`), so changing M requires a full
  index rebuild.
- **Consensus/replication machinery** — single-writer SQLite + CAS watch claims (a fencing-token
  pattern) is the correct topology for single-node deployment. Import distributed-coordination
  complexity only when Pillar 3 actually ships multiple writers.
- **Multi-worker Gunicorn** — models (BGE-M3, reranker, NLI) are in-process singletons (~2.5 GB
  each); ChromaDB PersistentClient assumes single-process access; `persistence.py` uses a global
  `_db_lock`. Multi-worker requires extracting a state-access interface first (Pillar 3).
- **Fencing tokens for job leasing** — DDIA ch8 correctly identifies clock-skew risk, but
  single-worker deployment means this is only a concern when multiple processes share SQLite.
- **Async translation with asyncio.to_thread()** — the `_translate_lock` only covers tokenizer
  mutation and batch_decode (`translation.py:89-132`); `model.generate()` already runs outside
  the lock. The code already runs in FastAPI's threadpool via `run_in_threadpool`.
- **Batch embedding for agent sub-queries** — tools already run in parallel via ThreadPoolExecutor
  (`agent/nodes/tool_executor_node.py:122-129`); each sub-query calls `embed_query` concurrently. Batching
  would require API changes and the throughput gain is unverified.

### Release mechanics

Branch `v2.6-dev` from `v2.5-dev` merge point · bump `VERSION` in `config.py` · README keeps its
"What's New" table convention (`v2.5 | v2.6` columns) · eval gate re-thresholded after Milestone 2 ·
integration seam suite extended for reconciler, admission control, and agent token streaming.

## Appendix — Review of external DDIA analysis (2026-08-23)

An external analysis was reviewed against the actual codebase. Key corrections:

### Factual errors in the external analysis

1. **Translation lock scope**: The analysis claims "_translate_lock serializes all translations
   across requests." This is wrong. The code comment at `translation.py:89` says "ponytail: lock
   only covers src_lang mutation + tokenize; inference runs concurrently." `model.generate()` at
   line 124 runs *outside* the lock. The lock only covers tokenizer setup (lines 90-92), batch
   tokenization (lines 117-120), and batch_decode (lines 131-132).

2. **ChromaDB process-safety**: The analysis claims "ChromaDB's PersistentClient is process-safe"
   and suggests Gunicorn multi-worker. This is wrong. ChromaDB uses SQLite internally; concurrent
   writers from multiple processes cause lock contention. The codebase uses a process-wide
   singleton with double-checked locking (`vector_store.py:97-120`), explicitly assuming
   single-process. Models (BGE-M3, reranker, NLI) are in-process singletons (~2.5 GB each);
   4 workers = ~10 GB just for models.

3. **OpenRouter Content serialization (BUG-03)**: The analysis claims this is an open bug. It's
   already fixed. `openrouter.py:19-36` has `_flatten_contents()` which explicitly walks
   Content/Part objects and joins `.text` fields. The docstring says "str(contents) would emit a
   Python repr, not the real text, so walk the structure and join the actual .text fields."

4. **_init_backends race (BUG-05)**: The analysis claims this is an open bug. It's already fixed.
   `llm_client.py:56-61` has double-checked locking: `if not _backends: with _backends_lock: if
   not _backends:`.

### Proposals for things already shipped in v2.5

1. **Event-sourced ingest pipeline**: The analysis proposes "Make ingest_log the single event log.
   Every mutation is an append-only event. ChromaDB, BM25, and caches are projections." This is
   exactly what v2.5 already did. The ingest_log IS the event log, reindex.py replays it, and the
   indexes ARE derived views.

2. **cache_refresh.py subscribing to ingest events**: The analysis proposes "Add a cache_refresh.py
   that subscribes to new ingest events." This already exists — `cache_refresh.py:11-42`
   (`_post_ingest_refresh`) folds new chunks into BM25 and invalidates retrieval/tool caches.

3. **Write-ahead intent log**: The analysis suggests adding `pending → committed → indexed` status
   to ingest_log. But v2.5 already has classified rollback (`vector_store.py:330-383`) and the log
   is written *after* indexes succeed ("the log never claims chunks that failed to land",
   `ingest.py:267-270`).

### Missing high-impact items

The external analysis misses the highest-impact optimization opportunities:

1. **NLI faithfulness on the synchronous critical path** — runs on every `/query` and `/chat`,
   adding seconds per answer. This is the single biggest p95 win.
2. **Cross-encoder rerank ~11s floor** — 15 candidates on CPU, the dominant retrieval cost.
3. **Threadpool starvation** — heavy queries share ~40 anyio threads, starving `/health` and job
   polls.
4. **llm_cache not invalidated on ingest** — deleted-paper answers servable for up to 10 min.
5. **Orphaned HNSW segments** — ~25 UUID dirs in `chroma_db/` that Chroma never GCs.
6. **SQLite single-lock forfeiting WAL concurrency** — commit-per-call, no read connections.
7. **BM25 tombstone compaction** — df rescanned per query term against tombstones.
8. **Deadline-aware failover** — 180s worst case, code itself names the fix (`config.py:400-402`).
9. **SSE backpressure** — producer blocks 30s/chunk on slow clients.
10. **Scoped queries bypass retrieval cache** — key already hashes the filter.

### Design rationale ignored

1. **BM25 JSON format**: The analysis suggests switching to MessagePack but ignores the deliberate
   security rationale at `bm25_search.py:175-176`: ".json.gz, because that is what it is — naming
   a JSON file .pkl invites the next reader to reach for pickle.load()."

2. **HNSW M immutability**: The analysis suggests bumping M=32 but doesn't mention that M is
   immutable after collection creation (`vector_store.py:151-153`). Changing M requires rebuilding
   the entire index. The codebase already says "deliberately untuned pending an eval set"
   (`config.py:312-323`).
